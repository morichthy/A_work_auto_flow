## 结论与对前次解释的更正

这次超预算的主要原因不是正文块太长，也不是图片Base64被算入字符预算，而是**内部搜索结果与大段命中诊断共同消耗了供最终材料交付使用的output_chars**。去重后的待组装正文只有8,634字符；已成功组装正文6,555字符。内部搜索输出与诊断分别扣46,872和46,443字符，占成功扣费总量的93.33%。

前次只根据累计账本确认output_chars接近上限，未记录具体扣费来源，因此将正文/必要上下文展开列为可能原因。此次真实逐笔轨迹修正该推断：4个技术候选全部采用section，没有发生技术单元full回退；必要上下文存在但没有造成正文数量级膨胀。不能将这次分类数值倒填为前两次历史运行的逐笔结果。

产品默认值与上述计量行为组合不适合这次真实场景，但证据不支持“召回10本身必然过大”或“8万字符放不下相关正文”。应先修正内部工作量、交付内容和诊断的预算边界，再以质量/延迟复验校准默认值。本轮没有修改产品实现、服务器上限或用户配置。

## 消耗为什么被放大

### 内部搜索重复文本

21次搜索输出共195个摘录/命中片段出现次数、46,872字符（excerpt=18,231、matched_text=28,641）。按固定引用和文本SHA256去重为55个片段、12,546字符，重复出现量34,326字符；增加excerpt/matched角色作为去重键后结果不变，说明本次未观察到两种角色之间同文重复，重复来自同角色跨路由/命中出现。该数不等价于34,326个token或可直接节省的模型费用。

搜索路由需要保留来源与名次，但不必在每次内部返回中重复用外部上下文额度为相同正文扣费。当前融合去重发生在这些搜索费用之后，无法回收已经累计的字符。

### 诊断不是少量标签

46,443字符的诊断可继续拆分为：

| 诊断类别 | 字符 |
| --- | ---: |
| 候选hits、query_sources、fusion_score、protected_terms等 | 40,668 |
| 查询计划 | 1,380 |
| 各路状态、警告和耗时 | 2,464 |
| 层级重排诊断（仅成功扣费） | 1,156 |
| 候选级排序信息 | 775 |

40,668字符中，matched_text原文为9,663字符，其余31,005为固定来源身份、路径来源、排名字段、其他元数据和JSON结构。相同命中因query_source不同继续保留；这些文本此前已经在内部搜索结果中计量。示例：概览正文650字符，其候选命中/来源诊断扣8,351字符，约为正文的12.8倍。

仪表diagnostics事件的json_chars采用默认JSON空格，仅作结构参考；以上正式扣费均以原charge_diagnostics的紧凑JSON实际charge.requested为准。

### 正文块与图片核对

共33次part尝试，对固定ref+selector+文本SHA256去重为23项、8,634字符；最大尝试块691字符。这只是实际走到的候选正文范围，不代表预算无限时的全库所需内容。成功加入17项、正文6,555，其中direct=5,935、required_context=620；成功正文没有同固定身份/选择器/文本的重复扣费。另有6次正常去重跳过、10次预算省略；省略正文按固定身份去重为2,079字符，不能把所有skip都解释为预算失败，也不能据此推断完整最终响应只差2,079字符。

四个技术candidate_packet均为section，包含显式命中块及必要上下文。七个概览/经验/经过候选为full，但各正文都不超过650字符。此次没有证据将整单元回退或递归展开归为主因；代码中这些分支是否适合其他场景仍可另行验收。

准备的packet中图片data_url合计557,888字符，不计output_chars；实际计费只包含97字符图注及读取字节。图片编码仍可能造成将来成功返回体膨胀，但本次最终value=null，没有把这些图片交给主AI，也没有看图/解码或生成note。
