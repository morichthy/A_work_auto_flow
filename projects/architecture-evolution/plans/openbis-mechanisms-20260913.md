## 本项目已经具备什么

核对当前文档及实现，而非只看目录或宣传定位：

- `automation/scripts/memory/store.py`：请求幂等、Owner 写锁、预期 HEAD 比较、暂存内容回读、记录/清单哈希、不可变提交目录、HEAD 原子切换。
- `automation/scripts/memory/service.py`：固定来源校验，提交前再次检查，保存成功后独立同步索引；失败返回 INDEX_PENDING，允许补偿而非重复记录。
- `automation/scripts/run_capture.py`：run-execute 固定 Python 脚本与输入，为每次执行新建输出目录，捕获 stdout/stderr、退出码和产物，失败仍留记录，执行后检查输入变化。它是显式调用的受控执行入口，不是任意工具工作的后台捕获器。
- `docs/AI_READING.md`：阅读会话有固定候选、正文阅读、理解笔记、预算和恢复；阅读记录不自动晋升为规范结论。
- `docs/CORE.md`、`docs/MEMORY_STORAGE_EXPLAINED.md`：原件/规范记录/检索索引分离；技术、经过、经验及概览可固定引用，关系导航、科学支持、复核状态分开表达。

因此，不能再把“有版本、哈希、追溯、事务、自动记录”这些标签整体列成本项目缺项。需要比较覆盖范围、失败恢复和实际工作入口。

## openBIS 的可借鉴差异

| 机制 | 官方资料支持的能力 | 与本项目的实际差异 | 借鉴建议 |
|---|---|---|---|
| 自动登记及完成判定 | DSS Dropbox 按目录触发，可等待静默期或完成标记，读取 metadata.json，界面查看每次导入状态与失败日志 [S1] | 本项目有受控 Python 执行捕获；其他工具产物依赖显式登记或 AI 按 Skill 写回，自动入口覆盖更窄 | 优先借鉴“完成事件→事实采集→确定归属→登记回执”；文件出现不能等于完成写入 |
| 字段体系与模板 | 对象类型、属性类型、必填/唯一约束、受控词表、校验及计算字段 [S2] | 本项目已有规范 schema，但没有核对到与之等价的通用领域属性配置界面 | 给高频任务少量模板，让程序填事实、AI 填解释，减少同一指标名称或单位写法漂移；保留完整技术正文 |
| 原文件的版本与恢复 | 7.x AFS 允许修改；覆盖产生旧版本快照，删除进入回收站 [S1] | 本项目规范记忆有历史，外部原件主要保留引用和哈希；“能发现变化”不保证“能取回旧字节” | 对正式产物或已授权快照增加可恢复性；外部原件仍只读，不把全部共享盘纳入托管 |
| 元数据和文件共同提交 | 7.x 可用 AS+AFS 两阶段事务；默认关闭，需配置，不能泛指 DSS 或任意 API 调用 [S3] | 本项目 MemoryStore 是单 Owner 规范记录事务；脚本运行、产物生成和后续记录不是一个全局事务 | 借鉴一致性边界与恢复回执。优先补“产物已落盘但登记未完成”的可重试处理；无必要不引入跨服务两阶段提交 |
| 可读的对象变更历史 | 属性前后值、作者、时间、父子关系及归属移动可查看 [S4] | 本项目保留记录修订及复核历史；不等于每种对象都有同等细粒度的业务差异展示 | 差异页优先回答“哪个参数、依据、结论及关系变了”，帮助 AI 和人复查 |
| 外部大文件管理的复用 | oBIS 外部模式只在 openBIS 管元数据，底层使用 Git/git-annex 跟踪外部内容 [S5] | 本项目外部引用不等于已经管理文件副本与存储位置 | 这是具体的避免造轮子示例：出现大文件版本/副本管理需求时，评估成熟工具，不自行发展一套通用大文件版本系统 |

这些差异主要证明 openBIS 的工程覆盖更广，不能证明其检索、经验综合或实际速度优于本项目。自动解析元数据仍是登记机制，不等于 AI 理解实验意义。

## 版本边界纠正

上一轮“openBIS 数据集不可变”须限定为传统 Dataset/DSS。7.x 官方推荐新的 AFS，可变文件有快照与回收站。[S1] AFS 是 openBIS 的 Atomic File System/File Server，不应混同其他同名 AFS 产品。

7.x 用户文档称 8.0 将移除 Dataset，API 文档则称 DSS 在下一版本可能移除；两处措辞并不完全一致。可靠结论是处于迁移期，不能据此声称 8.0 已发布或迁移已完成。[S1][S3] Dropbox 与 oBIS 的传统 Dataset 路径可作为机制参考，若要直接采用，必须核对目标版本的兼容性。

AFS 快照、回收站和哈希都不能单独替代独立备份。也不能把托管机构的备份服务等同于每个自行部署实例自带的能力。

## 对“AI 融入工作并自动记录”的具体启发

建议将确定性事实采集与 AI 解释分开，复用现有存储和索引接口：

1. 工具完成一个动作时，适配器产生稳定的事件身份、输入/输出指纹、命令参数、退出状态和归属候选。根据工具完成信号或文件完成标记登记，不凭修改时间猜测已完成。
2. 程序尽早保存事实和失败，AI 根据任务补充方法、原因、结果解释、适用边界与固定依据；重要阅读理解保留在现有阅读会话。无需逐项询问用户是否保存。
3. AI 中断时，应能发现“事实已有、解释未完成”的工作；恢复时继续已有任务，不重做实验或重复产生记录。优先由既有 Run/提交回执推导进度，只有无法推导的阶段才增加持久状态，避免第二套权威记录。
4. 保持“记录已保存、索引已可查、解释已完成、结论已复核”各自明确。记录所有有价值的失败，并不意味着给失败结果错误地标记科学通过。

这是本轮提出的实现候选，不是现有后台能力。openBIS 提供前半段可靠登记的参考，本项目的核心价值需要由后半段实际 AI 工作与经验复用证明。

用同一任务验证：正常完成、工具失败、AI 中断、重复事件、文件未写完、产物已保存但登记失败、索引失败。观察事实遗漏率、重复记录数、恢复后是否继续原任务、AI 解释是否忠实引用固定来源，以及以后任务能否检索并正确复用。现有原子提交与索引补偿应复用，不能因为换入口重造。

## 直接复用与只借鉴的边界

- **直接集成候选**：如果未来已经使用 openBIS 保存某类实验/数据，可用官方 pyBIS 作为 Python 适配入口 [S6]，本项目仍维护自己的 AI 阅读与经验记录。pyBIS 不是脱离 openBIS 的通用本地记忆库。
- **可独立评估候选**：官方将 AFS 描述为可独立于 openBIS 使用 [S3]；因此它比“整体接入 openBIS”更值得检查组件边界。但本轮未核验独立部署、Windows 离线打包、许可文件及兼容升级，不把可独立使用描述等同于可直接嵌入。
- **机制参考**：完成标记、结构化导入、失败历史、领域模板、字段差异、可恢复文件版本；适合先在现有架构上验证。
- **暂不照搬**：样品/库存体系、机构级管理和全局分布式事务。它们不是当前 AI 工作闭环所必需；未来有真实需求再评价。

后续其他项目也应按“工作中产生什么事实→怎样交给 AI 阅读与判断→怎样记录→怎样恢复和复用”检查。具备聊天、向量库或连接器并不足以判为强相关，更不能自动推出整体替代。
