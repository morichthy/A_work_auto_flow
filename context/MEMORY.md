# 历史记录、确认与纠错约定

本文件定义工作区记忆的实际操作。它不依赖某个模型的隐式记忆，也不保证聊天里的每句话已存入文件。

## 保存多少

Research 与 Project 默认采用同一标准。实质技术设计、分析、开发与阶段整理按有用内容保存技术单元、经过、经验/概览，不能只登记 Run 附件；完整成果按阅读需要编排，不强制双文稿。纯开发文档、规范整理、排期及简单查阅可用已有完整文档或计划/摘要，不补造技术经验，已有显式策略优先。对话中的有用中间记录由AI主动提交，无需用户逐条指定；重要结论/当前成果保存、阶段总结或交接按 [整理更新当前成果](../automation/workflows/consolidate-results/SKILL.md) 维护文稿与上下文一致性。记录要求不等于后台自动生成，局部提交不代表阶段同步。

当前 L0–L4 是所有 Owner 共用的内容压缩、发现与展开层级：L0 保存原始材料追溯，L1 是完整技术/方法/分析单元，L2 是研究、实施、使用、排错或决策经过，L3 是区分观察/结论/假设/建议的可复用经验，L4 是 Owner 顶层概览和发现入口。L1 的检索说明与稳定完整正文块分别维护；按技术内容保存必要定义、参数、公式、推导/计算、结果与限制。只有实验单元必须绑定实际 Run；方法与推导不虚构执行。预期长期复用的新建或实质更新 Owner 至少维护一条自足 L4；短经验可只有 L4 全文，其他层仍按实际内容允许缺失。定义集中在[记录标准](../docs/RESEARCH_RECORDING.md)。

新 narrative/overview 与分类 experience 采用 v4；L1/文稿仍为 v3，保留旧形状 v2 的明确读取路径。工作台每层只有一个入口；旧 event/map 经实际整理、固定前版来源后保存同一 ID 的新修订并更新索引，不自动改名。旧 v1 修订保持字节和固定引用不变，读取时将其 L1/L2/L3 投影为 L2/L3/L4。Run 元数据不能自动冒充完整技术单元；原始日志、完整数组、规范事务历史默认不进入知识正文索引，按固定来源追溯。

独立 `document_section` 组织固定技术块与必要定义，`document` 分别组织 `research_process` 完整研究过程和 `research_report` 精简研究报告；二者 `level=null`，L4 维护整体概览，旧 `map.payload.report` 仅保留兼容。修改前按目录和章节上下文读取，依据修订、新单元与变化关注只提出影响提示，复核后局部修订文稿，不能自动替换固定证据。

新 Run 优先用 `new-run --owner 对象ID` 保存到对象自己的 runs/；根 runs/接收无归属轻量任务，Project 用于大型或系统工作。框架文档与计划整理可直接在本次计划/摘要记录；有独立验证产物时再用 Run。全局模块影响以 [ARCHITECTURE](../ARCHITECTURE.md) 为准，必要快照保留历史，不维护第二份当前定义。

| 工作 | 保存方式 | 何时建立独立 Run |
|---|---|---|
| 看文件、查字段、改拼写、重试同一命令 | 必要任务摘要，不逐次归档工具输出 | 通常不需要 |
| 一组探索、调参、清洗或比较 | 一个任务级 Run；步骤追加到 `steps.jsonl` | 输入快照、配置、独立结果或需要复用时拆分 |
| 正式分析、数据变换、仿真、诊断、报告依据 | 独立 Run，失败和反证也保留 | 必须能单独解释和复现 |
| 可长期复用结论 | Run 复核状态 + 对应核心算法卡、数据卡、ADR 或模式 | 不为同一结论复制多份正文 |

`steps.jsonl` 为约定格式，需要时由 AI 创建，当前没有后台捕获器。AI 逐条追加时间、操作/命令、配置或脚本引用、输入/输出引用、执行状态、必要摘要；不保存私有思维链、重复终端输出或敏感凭据。重要独立尝试保留自己的输入参数和结果，不能被汇总抹去。

Run 的 `keywords` 建议 3–8 个领域词，覆盖对象、方法、异常、数据 ID；可添加中英文同义词。AI 按实际内容填写，CLI 不调用模型自动提词。检索覆盖标题、问题、结论、关键词、核心算法/数据 ID、参数和限制；中文子串，空格分隔词按 AND 匹配。步骤细节先通过父 Run 定位，再按需读日志。

`search-runs` 即时读取约定位置的 Run manifest，`refresh-index` 生成导航。材料检索使用 `search-knowledge` / `retrieve-context`，按角色、选择和预算装载。规范记忆使用 `memory search`；`knowledge` 默认查技术说明与知识，文稿/章节用 `documents` 模式，L0 用 `trace` 与实际固定选择。`memory document` / `section-context` 按文稿组织读取。两条检索路径的 Q/CTX 与 QMEM/PKT 回执不能混用，细节见 [检索手册](../docs/RETRIEVAL.md)和[记忆使用指南](../docs/MEMORY_USAGE.md)。`build-context` 仍是导航快照。反馈不等于业务复核。

## 谁确认、何时确认

- AI 可自动保存工作记录、候选结论和可执行检查结果，无需用户逐次批准“记住”。
- “把这个留着”“先记下来”：只表示保存，不表示结论正确。
- “我核对了原始记录，确认这个结论在某范围内成立”：记录为人工复核，引用该次确认、范围及证据，不冒充独立实验验证。
- “这次分析靠谱”：对象明确时可登记用户确认；未说明的范围不得自行扩大，证据可明确记为“用户判断，尚无独立复核”。影响关键用途而范围不明时再询问。
- 已有验证规则且用户已授权其作准时，AI 可依据结果登记流程复核；需说明规则/版本、检查产物和范围。不是所有自动测试都有这种授权。
- 纯探索、草稿或未满足验收的分析保持 `not-reviewed`。检查通过不自动宣布业务结论成立。

Run 的 `status` 表示执行（例如 planned、running、succeeded、failed）；`review.status` 表示结论复核，二者独立。旧 Run 缺少新增字段时按未提供处理。

| 复核状态 | 含义 | 使用方式 |
|---|---|---|
| not-reviewed | 尚未确认 | 候选证据，明确不确定性 |
| accepted | 有记录的确认及适用范围 | 范围内优先参考，仍检查现实反馈 |
| disputed | 有冲突或疑点 | 暂停作为确定依据，等待复核 |
| retracted | 已确认不能沿用 | 保留历史，只用于追溯/反例 |
| superseded | 被新 Run 替代 | 沿 replacement_run_id 查替代项并检查状态 |

`review-run` 要求 reviewer、reason；accepted 还要求 evidence 和 scope；superseded 要求另一个存在的 Run ID。它登记判断，不校验签名、证据真实性或业务正确性。每次变更在同一 manifest 的 `review_history` 追加前后状态；同一 Run 的复核写入应串行执行。手工修改 JSON 可能绕过历史，正式复核应使用命令。

## 确认后发现错误

1. 记录新证据与冲突，给相关 Run 设置 disputed；证据已明确时直接 retracted。原执行状态、原数据、原结论保持可追溯。
2. `review-run` 返回已登记依赖中的受影响 Run；`search-runs` 动态传播 `needs_revalidation`，覆盖跨项目、多级 parent_run_ids。缺失父 Run 同样提示证据缺口。
3. AI 再检索这个 ID 在卡片、ADR、研究综合、数据血缘和报告中的引用，登记影响清单。命令不自动撤回这些文档，也不能发现未登记关系；发布过的报告需要更正说明。
4. 建新 Run 重新分析。新 Run 只有实际使用旧 Run 结果才把它放入 parent_run_ids；纯纠错关联写说明，避免把错误结果当输入继承。
5. 旧 Run 可标记 superseded 并指向替代项；卡片/报告引用新证据，保留历史说明。下游逐个复核，不能因出现替代项而自动恢复可信。
6. 若撤回本身有误，可用新的 accepted 事件恢复，必须提供新的依据与范围；历史撤回事件不删除。刷新索引和上下文。已打开的旧快照不会自动更新，下次复用必须回源检查。

人确认提高复用优先级；证据真实性、时效、适用域与当前反证始终优先。公司规范是决策约束，也可能版本过期；不同来源不能只按全局等级机械排序。

## 长期与接入边界

Run、研究和算法元数据中的 claims/dependencies，以及知识/报告逐文档 `.evidence.json`，现在可由程序检查。`review-claim` 绑定结论和所属对象版本、追加复核历史；`check-run`/`finalize-run` 检查正式记录，封存不等于科学确认。`retrieve-context --purpose formal --scope "范围"` 只导出合格结论；默认探索继续展示候选和失效风险。scope 在扩展链保留。

撤回、缺失、版本变化与循环通过 supports/input 传播到已登记下游；background/contradicts 不按实际依赖传播。旧文档链接到失效对象但没有类型时显示待分类提示。未登记或无链接的改写仍无法自动追溯，旧聊天内容不会撤回。使用方法和完整边界见 [证据准入手册](../docs/EVIDENCE_CONTROLS.md)。

项目文件保存可迁移证据；Codex 记忆辅助找线索；索引是可重建缓存。外部平台通过工具注册表、数据卡和 adapter 接入，逐个声明来源、版本、权限、失败方式，避免同时加载所有连接器内容。

没有守护进程监控任意脚本，助手按任务负责写回。文件不是备份；Git 已初始化，但没有自动远程备份或防篡改审计。清理按保留策略单独授权，不因“临时”分类自动删除。

`evidence-monitor` 可由助手或已配置的定时器重复调用，只扫描获准材料和证据引用，观察实验终态/依赖风险；不会执行实验或升级可信状态。观察日志保存在 `context/monitor/state.json`，页面用 `evidence-view --serve` 查看。重复文本、同字节材料、重复引用只产生比较候选，不算独立验证；观察时间和复核记录时间分开。详情见 [查看与监测手册](../docs/EVIDENCE_VIEW_MONITOR.md)。
