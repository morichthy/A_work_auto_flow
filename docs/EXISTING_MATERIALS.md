# 材料导入、检索与变更维护手册

现行说明核对日期：2026-09-09。文件登记、规范记忆、检索投影和研究文稿各有维护入口；导入成功不表示已经读完、完成索引或通过业务验证。

首次接入看“用户最少需要提供什么”和“批量导入”；日常使用看“可复制提示词”；版本变化看“算法与代码如何一起更新”。这些步骤由 AI 在任务中执行，不是后台服务。

这是使用示例，不是另一套必填表单。下面的名字、目录与 ID 都是假设示例，并未创建真实算法或项目。

## 用户最少需要提供什么

### 文件搬迁后保留历史引用

历史 Run 的文件路径不能靠修改旧元数据来“修好”，否则会改变固定证据版本。已获准搬迁的文件可以在 `retrieval/sources.json` 的逐文件条目中登记 `path`（现位置）、`relocated_from`（原引用中的精确路径）、`sha256`（原文件的完整 SHA-256），并保留来源 ID、敏感级别和启用状态。仅当原位置不存在时使用这份映射；原位置存在则仍读原位置。迁移目标缺失、指纹不同、映射重复、授权撤销或含符号链接/联接均拒绝；不自动寻找同名文件或追随多级重定向。

映射用于找回同一份证据，不表示新内容已获复核。先核验两端字节，保存登记备份，再更新索引并回读文稿；实际搬迁、登记和补偿回执保存在本次 Run。固定来源 ID 引用直接使用其现位置，旧路径引用通过上述字段兼容。公共升级保留用户来源登记。

核心算法仅指公司算法/模块文档定义的关键模型算法，准入标准见 [核心算法规则](../core-algorithms/AGENTS.md)。接入前先确认文档定义的算法项及工程目标，不因脚本含函数、类、数值计算或被称为“模块”而建卡。未确定资格的材料留 inbox/research；普通辅助功能归 tools、automation 或 runs。

建卡使用 `new-core-algorithm <slug> --title "名称" --source-document "公司文档名称/编号或受控路径"`，补文档版本、章节、实际阅读状态及算法协同关系。source_document 仅是来源登记，未知版本留空；公司文档原名保留，不把“模块文档”擅自改写为另一份文件名。

直接给名称、可访问路径，以及希望“保留原位登记”还是“纳入工作区”。知道版本、用途和验证结果就一起提供；不知道可以留空。归组、英文目录名、元数据格式和内部链接由助手处理。

例如：“将我提供的三个时间同步算法登记为相互关联的全局核心算法；独立脚本可以复制进来，大仓库保留原位，只登记函数入口；先不重新验证。”

## 助手实际整理出的样子

```text
core-algorithms/time-alignment/             # 一个全局算法，不属于特定项目
  module.json                      # MOD-ID、别名、关联核心算法/研究/工具
  README.md                        # 用途、假设、文档—代码版本映射
  code/                            # 需要时存放受控实现，外部仓库可只登记
research/<topic>/                 # 专题证据、资料、记忆与综合
  runs/<run-id>/                  # 本研究实际分析，跨对象通过 RUN-ID 引用
  memory/                        # 服务维护的规范记录与不可变修订
projects/<optional-view>/         # 可选交付目标，可保存自身运行并引用其他对象
runs/<run-id>/                    # 无业务归属的轻量任务；兼容旧根 Run
tools/scripts/                    # 可复用小工具
tools/packages/                   # 可复用代码包
inbox/                            # 尚未整理的小材料或路径清单
```

`docs/templates/CORE_ALGORITHM_CARD_TEMPLATE.md` 是详细参考。实际核心算法卡可以从下述最小内容开始，不要求复制模板里的所有空表和示例公式。

```markdown
# 时间对齐

- 核心算法 ID：MOD-SIGNAL-ALIGNMENT
- 用途：对齐两路采样信号的时间基准。
- 关键词/别名：时间对齐、时间同步、alignment、重采样；低采样率为相关问题。
- 文档来源：用户提供的设计文档路径及版本。
- 代码来源：仓库位置 + 固定 commit/tag + src/alignment.py。
- 入口：align_signals；若未定位，标记待定位。
- 验证情况：用户表示历史上使用过，本次未复核。
- 对应关系：文档“重采样”章节 → align_signals；仅登记，尚未比对实现。
- 待补：输入单位、采样约定、验证数据与验收条件。
```

助手写入 module.json、核心算法卡及可点击的文档/代码链接，再运行 refresh-index 与 index-knowledge。核心算法列表来自全局 core-algorithms/；关联核心算法与研究使用稳定 ID。外部文件必须在 retrieval/sources.json 逐个登记，卡片中的路径不会授权自动抓取。

## 三种来源怎样处理

| 来源 | 助手操作 | 不确定或变化时 |
|---|---|---|
| 小型独立脚本 | 先查是否实现已收录核心算法文档中的模型；只有对应核心实现进入 core-algorithms/<slug>/code。其余按用途放 tools、automation 或 runs | 脚本本身不是建卡依据；无文档依据的算法候选留 inbox/research，不把复制成功当验证通过 |
| 大型代码库的一部分 | 代码留原仓库；核心算法卡记录仓库、版本、相对路径、符号与运行入口 | 当前无法访问时照实写“仅登记，未核验”，不声称已经读过 |
| 技术文档/算法文档/报告 | 原件保留在获批位置或副本。整理存储为知识记录时，完整文稿必须是文档原文（切分 L1 正文块，保证组装与原文相同）；不同版本（如 v1、v2）必须建立独立记录，不得提交在同一记录中覆盖 | 标注来源/版本及已知确认范围，发现冲突保留两方证据，多版本分别建卡与建记录 |

外部来源写在核心算法卡中，不直接把仓库 URL 当作工具注册表的本地 `entrypoint`：当前工具校验接受存在的本地文件或目录；目录工具仍需在说明中写出实际调用方法。需要调用外部工具时，再在 `tools/external/` 建实际适配入口并登记。

版本固定后原文件仍可能被删除，路径引用不是备份。可访问性、版本/指纹和获批备份应分别维护。输入大数据不因为“接入算法”就全部复制进本工作区。

## 研究是否必须同时创建项目

纯文献研究可以只创建 `research/<topic>/`，无需额外项目。`new-research` 只建立研究 JSON、计划、证据台账和综合模板；资料阅读、证据整理与结论由助手在任务中完成。

仿真/分析用 `new-run --owner RES-ID --title "分析目的" --research RES-ID --module MOD-ID`，保存到该研究的 `runs/`。`--owner` 指定唯一物理归属，`--research` 和 `--module` 可重复表达关联；未指定 owner 时，单一研究、项目或单一算法可以确定归属，多个研究需显式选择。无归属轻量任务才使用根 `runs/`。单文件与工具对象使用专用运行目录，见 [分层记录标准](RESEARCH_RECORDING.md#文件归属)。不移动旧 Run 来凑新布局，不因多个引用复制一次实验。

新实验可由 `run-execute` 自动登记明确输入、脚本、本次输出和日志；已有文件用 `run-register` 固定当前版本。登记不会追认历史字节。AI 再将可复核过程保存为 L1 技术单元，决策为 L2，经验为 L3，主题关系为 L4。完整过程与简版报告用独立文稿/章节固定引用这些记录，L4 不再承担新文稿编排。已有 `map.payload.report` 只作为兼容入口。操作见 [运行登记](RUN_CAPTURE.md) 与 [记忆指南](MEMORY_USAGE.md)。

## 批量导入：先建清单，再分批融合

1. **限定来源。** 用户给目录或文件清单、用途和允许处理范围。AI 先列有界清单，排除缓存、构建产物和重复副本；大数据仅登记引用，不扫描整盘。没有指定材料时不创建虚构业务对象。
2. **保存进度。** AI 在 `inbox/<batch>/IMPORT.md` 保存批次目标、来源范围、清单和下一恢复位置；归属明确后可保存在核心算法或研究目录并从入口链接。这个清单是人工维护的文件约定，CLI 不自动解析它。
3. **按主题阅读。** 先读目录、摘要和代码入口，再针对主题读章节、公式和函数。批量可从每批 10–20 个小文件开始，按实际字数和格式调整。PDF/Word/扫描件依赖当前可用工具；抽取失败、OCR 不可靠或只读部分章节都如实记录，不能标成全文已读。
4. **提词与定位。** 每份材料写用途、3–8 个关键词、中文/英文别名、算法/核心算法 ID、版本、可引用章节或代码符号。关键词覆盖对象、方法、输入输出、异常或适用条件，避免只写“算法、代码、报告”。文件名推测与正文提取分开记录。
5. **融合。** 同一内容的副本只保留主要引用及别名；互补材料链接到同一核心算法卡；相互冲突的结论并列记录版本、条件和证据，未解决时保留疑点。外部导入文件进行记录整理和存储时，记录的完整文稿必须是文档原文（切分 L1 的正文块，保证记录组装成完整文稿时和源文档完全相同）；文档类的知识记录区分不同的版本，不要以不同版本的形式提交在同一个记录中（比如某个技术文档 v1 和 v2 版本需要建立两个独立记录，分配独立 record_id）。导入不等于晋升为已验证知识。
6. **接回导航。** AI 更新全局核心算法卡和 module.json 的别名/关联，必要时补可选项目视图；研究更新证据台账；工具更新注册表。摘要正文只维护一处，地图保留短标签和链接。
7. **核验本批。** 文件正文和元数据保存后执行 `index-knowledge`；仅保存文件或 `refresh-index` 不会立即向量化。规范记忆通过 `memory commit` 保存后检查独立索引回执，pending 时用 `memory reconcile` 补偿，不重复提交。汇报已读、部分阅读、未读、失败、重复引用、冲突项和下一批起点；刷新导航并 validate。选几个用户真实问题，检查能否找到正确文档章节、技术单元、代码函数和版本，把漏检词补进实际维护入口。

批次清单建议使用以下表头；按实际任务创建，不必逐个文件建 Run：

| 来源路径/别名 | 版本/指纹 | 阅读状态与范围 | 关键词 | 归属核心算法/目标卡 | 重复/冲突/失败原因 | 下一步 |
|---|---|---|---|---|---|---|

状态可用 `未读 / 部分阅读 / 已读 / 读取失败 / 仅登记`。来源敏感时用受控别名。每批写回后才能声称已保存；再次导入同一路径时比较版本或指纹，避免重复卡片。哈希相同只能说明字节相同；哈希不同不能独自证明算法变了。

## 问一个算法问题时，AI 怎么找上下文

先按 [检索入口表](RETRIEVAL.md#先选择入口) 区分材料：算法原文与代码使用 `retrieve-context "问题"`，按文件基线、角色和预算返回 full/brief/excerpt 证据包；对象内 L1 技术单元、事件、经验及地图使用 `memory search`，再按固定引用装载。两者未完全统一，不能认为登记原位文件便自动生成记忆。下面的地图、rg 和 search-runs 作为补充定位方式。首次接入还需把原位文件登记到 retrieval/sources.json，关联写 module_ids/related；来源可写 context_role、keywords 和 consistency，普通卡片中的纯文本路径不会自行抓取。

先由问题里的名称、别名、现象和输入条件定位全局核心算法入口，再读取匹配核心算法卡中的文档、函数与相关数据/接口。Run 用 `search-runs` 查，命中后检查实际版本、复核状态和 `needs_revalidation`，再读取必要证据。按相关性逐步扩大范围，不把整个资料库加入对话。

例如在工作区根运行（名称为示例）：

```powershell
# OR 查名称和别名；先查全局核心算法说明，再读取原文。
rg -n -i '时间对齐|时间同步|alignment' core-algorithms -g '*.md' -g 'module.json'
.\automation\workspace.ps1 search-runs "时间对齐"
```

`search-runs "时间对齐 低采样率"` 是 AND 匹配，不会自动扩展同义词；没有结果时分别查别名和核心算法 ID。`build-context --task` 仅将任务描述写入导航快照，实际检索和原文读取仍由 AI 完成。新生成的上下文包不会自动刷新已打开的旧会话。

文件证据包未解决时用 `context-feedback CTX-ID` 逐级补证，文件单源反馈用 `retrieval-feedback Q-ID`；记忆查询的 `QMEM-ID` 使用 `memory feedback`。保持各入口的用户选择和预算，不能互换回执。首次大量导入后，应以实际问题验证召回质量；当前没有“所有格式均可解析、任何问题均能自动找全”的保证。没有命中时先查未读清单、索引待办和关键词缺口，不从摘要之外编造证据。

## 算法与代码如何一起更新

**日常直接告诉 AI 变化就可以；复杂变更引用维护工作流更容易避免漏项。** Skill 固定的是检查方法，你仍要提供变更对象或范围。二者都不会自行监听代码仓库。

核心算法卡维护多对多的对应关系，每行表达一个可检查的联系：

| 文档位置与版本 | 章节/公式 | 仓库与固定版本 | 相对代码路径与符号 | 配置/测试入口 | 对应状态与检查证据 |
|---|---|---|---|---|---|

文档和代码分别记录版本；未提交修改另记文件 SHA-256 或受控补丁。行号只辅助定位，不能代替函数名与版本。对应状态用 `未核对 / 一致（注明范围） / 有差异 / 来源不可访问`，与 Run 复核状态分开管理。一个函数被多个核心算法引用时，所有对应行都要检查。

| 发生的变化 | AI 应如何维护 |
|---|---|
| 文件搬家、函数改名，语义未变 | 保留核心算法 ID，更新路径/符号和映射；检查调用入口；记录旧→新位置 |
| 仅文案或推导说明变化 | 核对是否实际改变假设、公式或适用范围；确属文案修订则更新文档版本与对应检查记录 |
| 公式、接口、参数默认值或实现变化 | 比较前后差异，标出对应关系待复核；更新相关卡片/契约，按风险验证新版本 |
| 核心算法拆分/合并、多个实现切换 | 记录旧 ID 与新 ID 的替代关系、选择配置及适用版本；检查全部调用方，不悄悄复用旧身份 |
| 新证据证明旧结论有错 | 按 MEMORY 追加 disputed/retracted/superseded，查下游并重做必要分析 |
| 旧版本或原件无法取得 | 标为无法完整比较，仅记录当前可见版本；不宣称前后等价或完整复现 |

AI 在核心算法卡的变更记录保存日期、前后版本、变化摘要、兼容性、影响对象、验证依据和未决项；较大变更可在核心算法/研究目录另建变更记录并引用。用核心算法 ID、旧路径、符号和 Run ID 搜索卡片、接口、ADR、研究、工具与报告中的引用，逐项写“无影响/待复核/已更新”及依据。

**正常升级不使旧版结果自动失效。** 旧 Run 保留当时输入和代码，新版验证建新 Run；只有真实消费旧结果才登记 parent_run_ids。发现旧结论本身错误时再撤回。依赖检查覆盖已登记的 Run、claim、文档及记忆引用，无法推断未登记联系；变化不会自动启动重新实验或改写报告。按 `evidence-status`、`memory impact` 或 `document-impact` 的对象边界检查实际下游。

`new-run` 自动探测的是工作区 Git 状态，不一定是外部算法仓库；AI 必须在实际 Run 中补正确仓库、文件版本/指纹和环境。源码 checkout 可以有 Git，发行解压目录也可以没有；以实际回执为准，路径与哈希都不是原件备份。

## 可复制提示词

**整理：**

> 整理 inbox 中【本批范围】。读取 context-maintenance 工作流；分批建立阅读清单，保留来源、关键词和未验证状态；融合到已有核心算法/研究，原件不移动，列出重复、冲突和未读项。

**大量导入：**

> 材料在【路径清单】，用于【系统】。保留原位，先做有界清单，再分批阅读；每批写回进度、关键词、核心算法卡和文档/代码映射。不要把仅登记标为已读。用【三个问题】检查检索是否能找到原文与函数。

**同步变化：**

> 【核心算法】从【旧版本】变为【新版本】，变化在【文档/仓库/函数路径】。按 context-maintenance 的变更模式比较并更新对应关系，查下游影响，区分旧版证据和新版待验证项；缺失旧版本时明确说明。

**算法问答：**

> 关于【算法/现象】的【问题】，先按核心算法地图和别名找相关文档、代码与历史 Run。回答引用实际章节、函数和版本，标出未读材料及证据缺口。

**交接：**

> 保存本批导入进度、已读范围、冲突和下一恢复入口，更新 NOW；下一次从未读清单继续，不重复导入。

上述 context-maintenance 指 [维护工作流源](../automation/workflows/context-maintenance/SKILL.md)，可直接让 AI 读取文件。已安装轻量入口，可在客户端发现后使用 $context-maintenance；方法正文仍只在工作流源维护。
