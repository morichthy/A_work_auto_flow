# 研究分层记录与阅读标准

本页定义所有Owner共用的分层记录标准，现行v4聚合契约兼容v1–v3。默认由work-loop按有用内容选择记录，层级表达内容职责，不是可信程度。小操作可不新增记录，缺层正常，不因目录类型要求补齐或自动生成双文稿。技术正文、固定来源与实际回读要求不变。模块职责见[ARCHITECTURE](../ARCHITECTURE.md)。

## 所有Owner的共同默认

Research、Project、核心算法、工具、数据、知识、报告和Run都可保存L0–L4。默认retain允许全部层、granularity=normal、auto_summary=false，由AI在有用内容/交接节点保存，不后台生成或要求补空层。Research/Project保留mode=explore兼容标记，其余basic；这些标记不构成不同工作流程。已有Owner显式策略不改写，inspect返回有效值及来源。

原文方法步骤可写L1（method、run_ref=null）；文献明确记载的经过或本次实际取舍可写L2，必须区分是谁做的。用途/接口/适用条件可写L4；有独立复用价值的观察、主张、假设或建议写L3，注明来源叙述、AI推断或本次验证。纯概览可直接固定引用L0，不造L1/L2。未提取或未索引原文细节仍须报告缺口。

有实际产物的独立执行用Run，重要选择、失败与可复用分析按内容记录。文稿按实际交付/阅读需要编排，可只维护一种；若交付两种必须依据一致。每个事实只有一个权威归属，其他对象固定引用，不复制。

阅读会话的 note 与 `exploration_clues` 是工作中的理解和导航候选，不是 L0–L4 规范记录。只有在实际阅读、固定依据和适用条件足以支持时，才按本页将有复用价值的结果另行保存；潜在线索保留其依据、条件、未知和下一步，不能自动晋升为经验、关联或已复核结论。quick note 只依据实际交付的召回片段，不能冒充完整文稿阅读。

阅读 note 只写材料中对搜索有用的知识与研究演进，不重复当前搜索问题，不写 reader 的操作下一步、理由或结果；有依据的材料建议用“可选的下一步建议”。主 Agent 制定联想问题和关键词，reader 按给定文本检索并报告材料线索。

L0–L4、Run、document/document_section 的正文均在事实、公式、结果与关键判断旁就近引用固定依据，并与文末来源对应。已有结构支持块级 evidence_refs 时保存准确的块级关系；否则在正文使用明确来源 ID 或可解析编号并登记固定引用，不新增不受支持的契约字段。引用保持实际 ID、revision、SHA-256 和 locator；文件与 Run 的修订字段按其真实契约填写。历史只有记录级来源而无具体位置时明确缺口，不按来源列表顺序猜测句级或块级映射，不改历史字节；确需补齐时经实际审查提交新修订。

## 每条记录必须独立可读、可以正确复用

这项要求适用于所有 Owner 的新建和修订记录。读者只拿到**本条背景、正文及其必要定义**，不读聊天、相邻条目或整篇文稿，也应能说明：对象是什么，为什么记录这一条，在什么条件下做了什么，得到了什么，以及何时不能使用。独立可读不等于独立证明：固定来源仍用于核验和复算，正文必须先讲清来源支持的关键事实，不能用“见上一轮”“同上”、记录 ID 或附件链接代替解释。

保留最小充分上下文，不规定字数，不机械复制整个项目背景。关键术语首次解释；公式给出变量、单位、初值及成立条件；比较写明对象、输入和评价基准。未知背景或依据明确标缺口，未完成内容可以保存，但不能称作可直接复用的完整经验。标题、关键词、检索说明、结构化字段和外链都不能替代正文；尤其 v4 阅读路径以 `body_markdown` 为正文，不能把背景、结果和限制仅放在 payload 中。

| 层级 | 单条内容至少要让读者理解什么 |
|---|---|
| L0 原始依据 | 材料是什么、由谁或哪次执行产生、针对什么问题、版本/输入条件、包含什么和怎样解释；数值列、坐标、单位及来源限制随登记说明或受控说明保存。原件保持只读，不把原始文件强改成经验；未展开原件不能声称已核验全文 |
| L1 技术单元 | 问题与范围、输入及方法、必要定义/公式、主要结果、限制与复算依据。独立抽取正文块时必须同时带上 requires_block_ids 指定的必要定义，不能只交付失去前提的结果块 |
| L2 研究经过 | 背景问题和起点 → 本条实际记录的尝试、选择理由、观察或失败、认识变化 → 简单结论及仍未解决的问题。只发生一步就如实写一步，不编造多轮演进；说明是原文记载、本次工作还是事后补写 |
| L3 可复用认识 | 在什么问题和条件下，有什么观察/结论/假设/建议；具体如何使用、为何有依据、关键反例及不能推广到哪里。结论可以是条件性判断，不强行写成操作步骤；假设保留验证条件，建议不冒充实测 |
| L4 整体概览 | 对象用途与问题边界、主要方法和必要术语、当前结果/阶段、限制及未决事项；不依靠展开下层记录才能知道对象研究什么、当前能做什么 |

形成记录的 AI 在**同一次任务中逐条做脱离上下文的回读**：只看该条实际交付的正文/背景（L1 含必要定义块；L0 含登记说明），核对上述问题能否回答。发现缺项先补齐再提交；保存后经公开接口回读对应版本，确认正文与固定依据一致。阶段成果还要检查文稿编排，但一篇连贯文稿不能代替逐条独立性检查。内容自查不新增“已确认”状态，也不将结构校验通过当作语义充分。

## 各类 Owner 如何使用同一分层

Owner 决定内容归属，层级决定内容职责；由 AI 阅读固定材料后通过公共 memory 接口写作，程序不会因创建对象或登记原件就自动生成五层经验。保留原文主张、AI 推断、本次验证的区别，按实际内容适度扩展含义，不改变契约或强迫每个对象补齐五层。

| Owner | 可按 L0 → L1 → L2 → L3 → L4 组织的内容（按需选取） |
|---|---|
| Research / Project | 研究或交付依据 → 方法/分析/实验 → 实际探索与取舍 → 条件性认识 → 问题和成果概览 |
| core-algorithms | 公司定义文档与实现版本 → 模型方程/接口/推导/验证 → 文档记载或本次算法演进与排错 → 适用域、数值或工程经验 → 算法用途和边界；仍须符合核心算法准入，普通方法不能因此建算法卡 |
| knowledge | 已采用身份的原文及出处 → 原文方法/解释/推导 → 原文明示的形成过程或本次分析经过 → 区分来源主张和本次认识 → 主题、用途和知识边界；原文没写过程就不编 L2 |
| tools / data | 版本化工具或数据登记 → 使用方法/数据处理与分析 → 排错、选择或治理经过 → 复用条件和失败经验 → 用途、接口或数据范围；不把文件存在当作已经理解 |
| reports / Run | 报告依据或实际输入输出 → 分析/方法说明 → 形成过程或执行中的有意义取舍 → 限定范围的认识 → 本报告/执行的目标结果和限制；Run 日志不代替 L2，执行成功不代表科学结论成立 |

一个事实只保留一个权威归属，其他 Owner 固定引用；为独立理解而简要解释必要背景不等于复制另一套权威事实。原文与规范记录分别维护，采用身份、索引和 AI 形成记录是不同操作。

## 五层各自保存什么

| 层 | 类型             | 内容                                                                         | 阅读方式                     |
| -- | ---------------- | ---------------------------------------------------------------------------- | ---------------------------- |
| L0 | 原始材料统一视图 | 已登记的输入、完整结果、日志、脚本及固定文件引用；Run 元数据另标当前登记快照 | 先浏览清单，再核验并查看原件 |
| L1 | detail           | 完整技术单元：实验、方法、推导或分析；检索说明与稳定正文块                   | 研究文稿与默认知识检索       |
| L2 | narrative（v4）  | 连贯说明路线、尝试、失败、选择理由、转折与实际结果                                   | 研究经过；关系可选           |
| L3 | experience（新写作 v4） | 条目化观察/结论/假设/建议，适用条件、证据、失败与迁移边界                                 | 经验阅读与检索；关系可选     |
| L4 | overview（v4）   | 对象介绍、用途/方法、结果或当前阶段、限制和未决事项                           | 总览与检索；关系可选         |

目标、路线、问题、检查点、复核，以及独立 `document` / `document_section` 保留自己的契约，level 为 null。默认材料关系显示 L1；更高层可按需选入。默认知识召回使用 L1 及以上；查独立文稿/章节用 `retrieval_mode:"documents"`，L0 用显式追溯入口，不因存在原始摘录或日志就进入常规全文/向量排名。明确选中固定来源时仍执行权限、版本与预算检查。

## 新经过、经验与概览的写作及展开

v4 的 narrative、experience、overview 均要求非空 `body_markdown`，它是实际阅读正文，不能只放标题或附件路径。结构化字段帮助检查完整性与定位，不在组包时重复拼出一份 JSON 正文。

- narrative：`question`、`stages`（每阶段 situation/action/reason/outcome/evidence_refs）、`limitations`；解释路线为何变化，操作日志仍留 Run。可选 `occurred_at`、`failure`、目标/路线/问题/Run 引用保留实际发生时间、失败分类与研究关联；不把迁移时间当发生时间。
- experience：沿用适用域、做法、证据与失败边界，新增 `knowledge_type`：observation / conclusion / hypothesis / recommendation。分类不是复核状态，假设不能因此变为结论。
- overview：`question`、`methods`、`results`、`current_stage`、`limitations`、`open_questions`；包含范围和未解决问题，不能省略负面结果。

新三类 payload 均明确 `process_refs`、`technical_refs`；经过/概览另有 `experience_refs`，无关联可为空数组。引用必须固定 record ID、正整数 revision、SHA-256；分别指向 narrative、detail、experience。技术块可加 `locator:"block:块ID"`，读取时补必需定义。主入口展开仅沿这些固定关系；旧经验可复用原 sources/evidence_refs 中的固定技术引用，不扫描同 Owner 全文猜关联。

旧 v1–v3 event/map 原字节、层投影和来源继续保留，但不自动充当新经过/概览。语义整理时实际阅读依据，创建新 narrative/overview 并保留旧记录引用；未知处说明缺口，不自动继承 accepted。L0、L1 及独立长短文稿职责不变。

## 文件归属

L0 自动汇总当前对象的 Run 登记和记忆固定引用，研究还汇总显式关联的 Run。同路径、同指纹的材料只列一次，并保留各使用对象和来源登记修订。`source` 是兼容的内部来源登记类型，用于独立来源或摘录；已有 Run 输入/产物不必再创建 source。没有登记的文件不会因放进目录就自动成为证据。

保存实验时，由 AI 用 `run-execute` 执行新 Python 实验，自动将明确输入、脚本、本次输出与日志登记进 Run 的 inputs/artifacts 并固定 SHA-256；已有文件及其他工具结果用 `run-register`，无需用户手填哈希。环境与参数仍需补充完整，入口不会发现所有隐式依赖。预览、恢复与失败状态见[执行手册](RUN_CAPTURE.md)。已有 L1 可继续使用固定 Run/文件引用。缺失指纹不补造执行时版本；缺失、权限撤销和版本变化均报告缺口。L0 导出是清单而非整批复制原件。CLI 请求与限制见[统一入口设计](design/L0_MATERIALS.md)。

```powershell
.\workbench.cmd new-run --owner RES-实际研究ID --title "本轮需要验证的问题"
```

目录型对象的 Run 位于 `<对象>/runs/<run-slug>/`。无归属任务使用根 runs/；Project承担系统级或大型目标。单文件知识/报告/数据对象使用自己的 `<memory_home>.runtime/runs/`，工具注册项使用 `tools/runtime/<tool-id>/runs/`，避免不同对象共用同一个父目录。

一次实验只创建一个原生 Run。实验类 L1 是固定引用该 Run 的技术说明，不是另一条执行记录；方法、推导和分析类技术单元按实际依据保存。一个 Run 可以被多个研究引用，但只有一个物理归属。旧根 Run、旧项目 analysis/runs 与已保存来源继续兼容；不得为整理目录直接改写原提交、旧来源哈希或 accepted 结论。

## 需要 L1 时如何写

v3 的 `unit_type` 为 `experiment`、`method`、`derivation` 或 `analysis`。实验必须绑定固定 Run；纯方法、推导和分析可令 `run_ref` 为 null，仍须交代固定依据或缺口。`retrieval_description` 简要说明问题、方法、发现、适用、不适用和限制；完整正文只存于 `blocks`，`body_markdown` 留空，避免两份正文漂移。块包含稳定 `block_id`、`role`、`markdown` 和 `requires_block_ids`；结果块可以依赖同单元的变量定义块。检索说明用于发现候选，不替代完整技术说明。

按照读者可以独立复核的顺序组织正文。可以合并短小节，但不能只留下题目、总评和附件链接。

1. **问题与范围**：本轮检验什么，为什么需要做，比较对象及预设可证伪条件是什么。
2. **输入与方法**：关键参数、单位、取值理由、样本数量、随机种子、假设、程序与环境。完整数组放L0，影响结论的参数在正文直接显示。
3. **公式与计算说明**：给出公式、变量定义和可核验的推导步骤；中间数值应能与脚本/结果对照。记录可公开复核的技术解释，不记录模型私有思维链。
4. **结果**：列出实际结果表，必要时给图与图注，说明坐标、单位及误差定义。图片引用固定附件和哈希，不能用无来源图片替代真实数据图。
5. **讨论与限制**：观察、反例、失败类别、适用范围、不能推出的结论、下一轮的问题。执行成功不等于方法总是正确。
6. **证据与复算**：固定 Run ID、来源 ID/版本/指纹、实际脚本及命令。未执行的计算明确标为推导或建议，事后补写标明补写时间。

例如，浮点误差必须区分精确实数输入和已经表示为binary64的输入：

\[
S_{\mathrm{ref}}=\sum_{i=1}^{n}\operatorname{Fraction}(x_i),\qquad
e_{\mathrm{abs}}=\left|\operatorname{Fraction}(\widehat S)-S_{\mathrm{ref}}\right|.
\]

这里 \(x_i\) 为实际传给程序的浮点数，\(\widehat S\) 为计算结果；本例输入无量纲，绝对误差也无量纲。其他研究应写自己的量纲、基准和假设，不能照搬该公式。

## 保存、回读与完整性检查

对话中的有用中间记录由 AI 自主判断并提交，无需用户逐条指定；不后台捕获全部聊天。明确保存重要结论/当前成果、阶段总结/交接或结果与边界实质变化时，执行 [整理更新当前成果](../automation/workflows/consolidate-results/SKILL.md)：完整读取当前概览与文稿，核对文稿固定版本至当前的相关新增/修订及未引用内容，维护必要记录、章节、概览与文稿根，再全文回读和检查工作上下文。中间提交允许先保存并列出待同步影响，不等同于阶段完成；用户明确只暂存或限制范围时遵从。

“本阶段完整成果已同步”仅在该 Skill 的范围/版本、变化处置、完整阅读、依据与一致性检查完成后写入现有任务清单/摘要；不是新契约字段或科学认可。索引状态单列：本范围明确要求的检索通道须完成相应检查，未要求的可选向量索引待处理不阻止正文一致性声明，也不能声称该通道已就绪。没有完整文稿的实质成果按需编排一份，不强制双文稿；纯规则/计划任务可维护已有完整 Markdown 成果并固定依据。程序的 complete/coverage/版本提示不替代 AI 实际检查。

当前工作台只展示统一的 L2/L4 层级入口。旧事件和地图迁移须实际阅读、提交完整 v4 新修订，并固定引用其上一修订，不能直接改规范 JSON；流程见 [旧内容整理](MEMORY_USAGE.md#整理旧事件和地图)。保存新经过后回读 revision/SHA，再修订经验与概览的展开关系，并重建对应对象索引。历史研究事实、失败执行和结论复核不随迁移升级。

需要执行的实验先完成原生 Run 与受控来源登记，再按 [请求示例](MEMORY_REQUESTS.md) 生成实际 JSON；方法、推导和分析按真实依据保存，不为字段完整虚构 Run。新 narrative/overview 默认 v4，新分类 experience 显式设置 `schema_version:4`；L1 与独立文稿继续 v3。其他旧种类默认 v3。未标版本的旧 detail 形状及包含 `map.payload.report` 的地图按 v2 兼容；显式 v1 仍按原契约解释，不能把旧 L1 事件当成新 L1 技术单元。提交封套和记录的 `schema_version` 是不同字段。

```powershell
.\workbench.cmd memory inspect RES-实际研究ID
.\workbench.cmd memory validate-draft --request .local/research-records.json
.\workbench.cmd memory commit --request .local/research-records.json
.\workbench.cmd memory inspect RES-实际研究ID
```

保存实际产生的有用内容并核对其固定依据；需要续接时记录下一步。缺层正常，没有独立经验就不生成空条目；未知事实明确缺口，不靠虚构字段通过校验。

保存回执成功后，还需检查逐条记录的正文、payload、固定来源以及索引状态。索引pending时按回执补偿，不重复提交同一逻辑请求。工作台研究文稿应能直接读到参数、公式、结果与限制；历史修订、L0原始附件按需展开。仅CLI成功或页面有标题不能算内容验收。

## 连贯报告的编排

L0–L4规定内容如何保存，不规定报告按什么目录阅读。工作台的“研究经过”页还提供独立文稿阅读：问题与范围、共同方法、详细实验、讨论、结论与下一步。L2 narrative 则是其中有依据的过程内容。先展开实验事实，随后综合经验；不要把五层各加一个标题直接拼接。

新文稿使用独立的 `document` 与 `document_section` 记录，两者 level 为 null。文稿保存目的、读者、范围、公共固定依据和有序 `section_refs`；章节保存标题、稳定 section_key、角色及有序 blocks。完整过程的 `document_type` 为 `research_process`，精简报告为 `research_report`，两者共享固定依据、独立组织正文。L4 overview 保存整体概览；旧地图经实际整理后用新修订迁入 overview，旧 `map.payload.report` 仅供历史固定阅读，不用于新文稿。

| 正文块            | 必填内容                        | 用途                                                                     |
| ----------------- | ------------------------------- | ------------------------------------------------------------------------ |
| `type: "prose"` | `markdown`、`evidence_refs` | AI 编写背景、共同方法、实验间的因果衔接、讨论与结论；就近固定依据        |
| `type: "unit"`  | `ref`；可选 `block_ids`     | 固定 L1 修订；省略 block_ids 读取整单元，指定非空列表时自动补齐必需定义 |

这里的 SHA 是固定记忆记录的 `record_hash`，不是正文文件的 SHA。先保存并回读 L1，再引用它提交编排。v3 单元显式传 `block_ids:[]` 会被拒绝；v2 detail 没有稳定块，不能按非空块 ID 列表选择，省略该字段读取原正文。没有事实主张的背景段可以没有证据引用；实际观察和跨实验判断应给固定依据。`discussion`、`conclusion` 放在详细实验之后，不能在正文展开前先机械展示高层地图。

连接段集中在编排中写一次，例如：“第一轮说明顺序会改变结果，但不能据此判断补偿算法是否可靠。因此第二轮采用三项抵消序列，比较补偿在每一步是否保住小量。”随后接相应的 detail 块。这段引用实际 L2 决策，而不是给每条 L1/L4 增加独立的“过渡字段”。

v3 L1 的正文块完整呈现问题、输入、算法步骤、关键中间量、结果与限制；共同方法可以独立为方法技术单元，再由章节固定引用。v2 详细记录继续使用原 `body_markdown`，原字节与哈希不改写。章节先提供必要方法和定义，再呈现结果；不能为了简短选取结果而遗漏其前提。

图片用标准 Markdown 形式就近放置，例如 `![第二轮六种排列的误差比较](figure:0)`，对应本 L1 的 `payload.figures[0]`。`figure:1` 对应第二张图，以此类推；每张图仍由固定来源引用、授权和字节指纹控制。没有占位的旧 L1 图示只补充展示一次。图号按报告阅读顺序确定；原始大数组和复算日志仍在 L0，不塞进报告。

### 修改与回读

1. 需要文稿时确定问题、读者和范围，保存实际需要的技术单元/经过，回读固定版本。
2. 按本次变化维护已有 L3 经验和 L4 概览（旧地图保留，整理为概览需另存新内容）；单独保存章节，再用其固定引用保存文稿。环境重试等过程可在附录交代。
3. 通过公共 `memory document` 回读整篇报告，再从开头到结尾审核衔接、重复、顺序、参数公式和图文一致性。没有编排的旧对象明确显示“尚未编排”，可以先查看原记录。
4. 先读取 `memory outline`，再用返回的章节记录 ID（不是 section_key）调用 `memory section-context`，获取目标章节、固定技术块与必要定义，按预算和选择清单局部修改。该动作的预算是 `budget:{"max_chars":20000}`，区别于普通材料包的整数 budget；预算约束返回给 AI 的正文，不代表底层只读取了一章。章节有变化时新增其修订，再修订文稿的章节引用；未变章节沿用原引用。
5. `memory document-impact` 比较固定引用和 `watch_refs` 基线，报告来源修订、失效和新增技术单元及受影响路径。变化关注不属于证据，不让新来源自动进入正文；AI 复核后才更新对应章节。无变化不制造新修订。
6. `memory document` 默认选择 `research_process`，可按 `document_type:"research_report"` 读取精简报告，也可按 `document_id` 与 revision 读取固定历史；同类型有多份时默认取最新更新的文稿，正式修改前应固定实际 ID/修订。没有独立过程文稿时可回退旧 map 编排；没有独立精简报告时明确报缺，不把旧长报告改标签。每次完成后检查 `document_source`、完整性、覆盖与版本提示并阅读全文，自查和人工待审分别记录。

来源被撤销、缺失或无权读取时，显示明确缺口并停止相应内容的正常组装；不能把旧截图、摘要或过渡段当作访问旁路。报告是经过整理的研究表达，保存成功与人工认可仍分别记录。

## 兼容与维护

v1 source/event/experience/map的存储层仍是L0/L1/L2/L3，展示与索引分别映射为L0/L2/L3/L4。原记录、哈希和固定引用保持不变；新L1只能从真实证据补写，旧Run缺说明时显示缺口。补写不自动继承原证据的accepted状态。

v2 detail 的原 `body_markdown` 和旧 map 编排继续读取；新写作采用 v3 技术单元与独立文稿，不把读时兼容误当成已迁移历史。当前聚合契约见 [memory-v4.schema.json](../automation/schemas/memory-v4.schema.json)；技术块规则见 [technical_units.py](../automation/scripts/memory/technical_units.py)，文稿选择、组装和影响检查见 [documents.py](../automation/scripts/memory/documents.py)。

正文与图表随所属对象保存。规范记忆由公共 CLI 维护；阅读目录、全文/向量和材料关系是可重建派生数据，不成为新的事实来源。用户修改的旧 Skill 升级时须按新版标准合并；框架安装器不能静默覆盖自定义指令。[重构计划](design/system-memory/L0-L4-REFACTOR.md) 保留历史范围与验证记录，现行行为以本页、当前契约和代码为准。
