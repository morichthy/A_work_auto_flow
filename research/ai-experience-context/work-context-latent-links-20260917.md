# 跨材料潜在联系：调研工作笔记

日期：2026-09-17。归属：RES-AI-EXPERIENCE-CONTEXT；本问题延续其“如何发现历史经验、扩展检索并控制成本”的目标。状态：公开文献定向调研与候选建议，未实施、未做本地效果实验、未晋升规范结论；本笔记不表示既有研究文稿已整体同步。

## 问题与阅读范围

用户关注：语义不相似的材料可能具有上下游联系；依据分散在文献、知识和实验相关性中，如何长期维护并在问题检索时发现。

本轮查阅公开原始研究、作者论文和官方标准。阅读范围为摘要、方法概述及定向正文，非逐篇全文审查、非系统综述。不上传工作区业务材料。网页查阅时间为上述日期；除 arXiv 明示版本外，本笔记仅保存链接，不声称已固定远程网页字节。

本地现状依据：上一轮已读 `docs/MATERIAL_QUERY.md`、`docs/CORE.md`、`automation/scripts/material_query/associations.py`、`automation/scripts/memory/associations.py`。当前已有关系导航核验固定端点与状态；旧接口能生成关键词/向量候选；自动结构提供器未接入。这些是已查代码的现状，不是本轮新开发。

## 文献与适用边界

1. Literature-Based Discovery（基于文献的发现）：经桥接概念连接分离文献，形成可验证假设。原始起点为 [Swanson 1986](https://pubmed.ncbi.nlm.nih.gov/3797213/)；[Cameron 等 2013](https://pmc.ncbi.nlm.nih.gov/articles/PMC4031661/)用有方向、有类型的陈述图重建和分解其假设。A–B 与 B–C 的存在只产生待检验连接，不能无条件推出 A 导致 C。
2. [INDRA，2023](https://link.springer.com/article/10.15252/msb.202211325)：规范化文献/数据库中的机制片段，处理重复与详略关系、估计抽取可靠性，结合实验共依赖数据寻找解释。Evidence 保存文献来源及可获得的上下文。抽取正确性与科学真实性不同；跨陈述的条件兼容、矛盾和因果传递仍是难点。它是生物医学实例，迁移到工程领域需另建变量、单位、对象与条件表示。
3. [ROBOKOP，2019](https://pmc.ncbi.nlm.nih.gov/articles/PMC6954664/)：通过图形化问题查询、排序和探索知识图谱中的回答子图，保留来源。证明有可用的路径查询范式；长路径会造成候选爆炸。
4. [HippoRAG 2，2025，查阅 v1](https://arxiv.org/html/2502.14802v1)：结合段落、抽取的关系与 Personalized PageRank（从查询种子出发、有返回倾向的图上随机游走），支持跨材料多跳检索。公开问答基准上的收益不能直接解释为工程发现或因果判断的收益。[GraphRAG，2024/2025](https://arxiv.org/abs/2404.16130)原论文侧重实体图、社区摘要与全局问题综合，两者目标不同。
5. [PCMCI，2019](https://pmc.ncbi.nlm.nih.gov/articles/PMC6881151/)：结合条件独立检验处理多变量、非线性及滞后时间序列联系。因果解释依赖假设，包括混杂覆盖等；少量零散实验笔记不能直接输入就获得可靠因果网络。
6. [AnyBURL，2019](https://www.ijcai.org/proceedings/2019/435)：学习图中的逻辑规则，生成带规则解释的缺失关系候选。候选需补证；稀疏、偏置或错误关系会限制效果。
7. [Wohlin，2014](https://www.wohlin.eu/ease14.pdf)：前向/后向引文滚雪球扩展文献集合。低成本、可复查；对没有引文联系的分离文献，仍需概念或机制桥接。
8. [W3C PROV-O，2013](https://www.w3.org/TR/prov-o/)：维护实体、活动、责任主体及派生来源的标准。用于回答关系从何而来，不负责证明关系为真。

## 对本项目的候选建议（AI 综合，未验证）

将检索单位从只有文档补充为实体、变量、过程和带条件的关系陈述。最小陈述需要：两端稳定身份及变量含义；关系类型与方向；工况/版本/时间尺度；来源段落或实验版本；证据类别；复核、失效、冲突状态。来源是一份证据还是多篇转述需区分，不能把转载数量当独立复现。

实验相关、文献主张、模型预测和干预证据分别保存。尚无解释的相关性允许留为候选；未观测不等于无效，负结果应有真实检验条件。存在共同上游、单位不兼容或工况冲突时，不应机械串接。

检索可并行保留直接关键词/向量路线和关系路线：从问题抽取对象、结果及约束，先找一批种子，再从已保存陈述沿上游、下游和共同影响因素展开；根据发现的中间概念生成新的定向检索。先试有界 2–3 跳，这只是起始配置建议，不是文献给出的最优值。尚无中间证据的路径显式显示缺口。

返回可检查的路径及每步证据，而非只有相似文档列表。排序比较条件相容性、证据质量、路径长度与不同机制的覆盖，抑制“系统、性能、影响”等过泛节点；保留少量弱线索的探索预算，避免直接相关性重排把桥接材料全部过滤。

先用现有存储承载少量关系陈述与证据引用，索引作为可重建投影；是否引入专用图数据库，待规模和查询需求证明。图谱构建、检索策略、假设复核保持独立。

## 未决问题与建议验证

- 尚未选取真实业务题集，无法确定哪类关系最有价值、抽取成本及错误率。
- 后续若开展实施，先选若干已知跨材料解决链路，比较现有混合检索、加显式路径、加新关系抽取/图传播三种方案。
- 评价目标：桥接材料召回、完整有效路径比例、条件不兼容率、错误关联、解决问题的实际帮助、延迟及阅读成本。
- 按时间切分材料，避免把后来已知答案带入早期发现评估；重复转述不当独立证据。
- 本轮只形成来源导航和候选设计，不声称提高了当前系统检索质量。

## 续问：作为默认 Owner 阅读不足后的加深路线

2026-09-17 用户进一步明确：默认保留“检索 → Owner → 完整文稿 → note”，只有无法提供较好结果时才启用联想式加深，最终交付可靠经验 note 给主 Agent。本节是待讨论建议，不是实施决定。

本轮定向核对了 `docs/AI_READING.md`、`reading.py` 的 recall/decide、`reading_owner.py` 的候选交付/read_owner/note_owner/handoff_value/expand_sources，以及 D34/D30/D28/D25 等相关开发决策。现有 expand 必须填写实际缺口；Owner note 的出处只从该 Owner 已交付集合解析；handoff 顺次装入完整 Owner note，超限或陈旧时省略并报缺口。引用列出与已展开正文在实现中分别记录，不能等同已读。未执行软件或真实 AI 场景测试。

### 建议流程

1. 默认路径足够就交接。reader 判断知识缺口，主 Agent 可在使用 note 后反馈实际失败；候选未续页、文稿未完整交付、索引/授权/模型错误先按原路径处理，不能作为已证实“需要跨域联想”的依据。不要求耗尽默认全部候选才允许转向。
2. 沿原 RS 的 expand 保存：原问题、已经尝试的办法、未解决环节、期望补到的证据。补查路线标为普通补查或联想；沿用现有 phase，不另建平行会话状态机。
3. 联想从已读文稿里的变量、过程、约束、失败模式及已登记关系出发。reader 提出少量桥接子问题，每项带起点固定引用、连接理由、需要验证的关系和继承条件。无来源的 AI 猜想可以作为探索方向，但必须标出待证据，不能直接成为有效路径。
4. 子问题单独调用召回，不冒充原问题的等义 query_variants。原任务目标不变。子问题适用条件与最终迁移条件分开：例如原设备型号未必适用于基础机制文献，但迁回原问题时必须重新核对。原授权上限、排除和固定来源要求始终保留。
5. 新候选仍交付 Owner 和有界正文；AI 按对子问题的帮助判断，选定后完整读文稿。现有关系入口产生的候选需要经正常授权和版本核验登记到原 RS，不能绕过“已交付 Owner 才能读取”的限制。再次遇到已读 Owner 复用有效进度；发现新的来源依据时允许定向展开，不用重新全文读取作为固定要求。
6. 每步记录来源主张、AI 推断、条件差异和验证缺口。新材料若填补机制则继续回接原问题；无新证据、重复路径、关键条件冲突或达到预算时停止该分支。Owner 阅读总量沿原 RS 计数；联想分支/深度/轮次应有明确上限，工程预算沿当前每操作保护，不错误宣称 Owner 模式已有全会话模型费用账本。
7. 逐 Owner note 继续作为工作底稿。在同 RS 增加可选的任务综合 note，正文复用现有 question/conditions/understanding/logic/details/sources/limitations/next_steps；另以最少结构记录关键判断对应的固定来源、路径和证据类别。只从本 RS 的实际阅读回执取证；引用已列出但未展开时，只能写“文稿引用某来源”，不能写已核验该来源。
8. 联想完成后，handoff 优先交付任务综合 note 与必要缺口，Owner 底稿可按需查看。综合 note 的每条关键连接绑定其依赖的固定来源和底稿版本，来源变化或底稿修订时标记相应综合内容待重验；不静默拼入旧判断，不让装包自动完成语义综合。默认未启用联想的会话可维持原交接行为。

### 可靠性的含义与最小开发范围

可靠 note 应让主 Agent 分清可直接用的经验、条件满足才可迁移的认识和未验证假设；若证据不足，可靠交付是准确的缺口和下一步，而不是必须写出肯定结论。程序核验实际交付、固定版本、范围、路径完整性和预算；reader 核对语义、条件、公式和反例；主 Agent 判断能否进入实际工作。关键高影响推断可另做定向复核，不能以自评通过当科学验证。

第一步建议仅完善原 RS 内的联想补查记录、桥接召回/候选接入、跨 Owner 综合 note 及交接失效校验。查询与固定读取复用现有实现；关联探索 Skill 负责方法，程序负责状态与边界。不立即增加图数据库、全库离线抽取或自动发布推断关系。长期可复用连接按现有规范写入入口独立保存，探索候选与已采纳导航分开。

待验证场景：默认已足够时不额外联想；原问题低相似但桥接子问题有效；发现已有关系外的新路径；错误链/不兼容条件被明确排除；没有连接时保留真实失败；来源变化后综合 note 不再按原样交付；预算/授权/旧 RS 兼容。先与当前默认流程作固定题集对照，衡量桥接证据召回、note 核心细节覆盖、无依据推断、最终任务帮助及成本，再决定是否增加图传播。

## 续问修订：以 note 驱动文本召回，缩小第一版

用户进一步提出：默认阅读时细化潜在关联信息；结果不足时据当前 note 生成搜索词和文本，重新召回、读 Owner 文稿、持续更新 note；工作台应能控制可选联想搜索文本。本节记录方案修订，未修改运行功能。

新增核查：memory-v4 的 AssociationPayload 已有 from/to、relation、explanation、shared_structure、transfer_limits、differences、basis_refs、candidate/accepted/rejected/withdrawn；这不等于逐关系的变量单位、定量滞后及证据来源类别已有完整结构化模型。ExperiencePayloadV4 有 applicable/prohibited/failure_modes/retry_conditions 和 observation/conclusion/hypothesis/recommendation 分类，但知识类型不等于实测/文献/AI推断等证据来源类型。material-query Skill 已要求问题连接、变量单位、固定出处、假设、反例与下一步；consolidate-results 要求纳入已有重要内容和未决事项，但均未强制逐篇提取待探索关系，更不保证每份历史记录实际填写齐全。本轮未做历史记录内容审计。

reading.py 的 start 将 query.association.mode 固定为 off；术语库 related 扩词是另外一条机制。不能把新增“note 驱动联想文本”做成通用关系补充开关的别名。当前 workspace_settings 没有此阅读选项。

修订建议：第一版复用文本召回闭环，无需先实现图遍历、图候选接入或独立路径服务。更新工作/阅读/成果整理 Skill，明确有实际内容时保存潜在线索、来源、连接理由、适用条件、待验证点；没有线索不编造。note 可增一个兼容旧会话的可选线索区，不必把所有技术细节变成新 schema 字段。

原 RS 内增加可选的联想查询说明：为何加深、取自当前哪条线索/哪个固定 note 修订、实际搜索文本及必要条件。实际关键词复用现有 recall 字段，由 AI 据搜索文本生成；语言变体在每个子问题内部仍保持等义。程序保存请求与修订，不自行用模板拼接替代 AI 推理。沿用 expand/recall/read/note 的动作，可做薄适配而不新增独立检索服务。

仍需增加会话级综合 note 的保存/引用校验能力：当前每 Owner note 限该 Owner 来源，不能仅改提示词就可靠保存跨 Owner 综合。沿用同 RS、同 note 正文字段和既有交接入口，底稿与综合正文职责分开；综合正文引用当前会话实际读到的多 Owner 依据。循环更新保留原有效细节、补充/否定关系和历史修订，不无条件累加全文，也不让最终装包自动代写综合。

工作台建议：新会话默认选项为“默认阅读不足时允许联想”，可关闭；本次显示可选“联想搜索文本”，支持 AI 生成或用户填写/编辑，展示其对应缺口和已执行轮次。设置页仅管理默认策略及有限轮次；本次文本属于 RS，不污染全局问题。编辑文本不应直接重写已执行查询或静默扩大授权。服务没有后台 AI：生成/更新 note 仍由实际 reader 执行，UI 负责保存与交接。

开发验证应覆盖旧配置/旧 RS 兼容、默认路径不额外联想、用户编辑查询和版本冲突、跨 Owner 来源校验、已列出但未读引用、陈旧综合 note、轮次/Owner/输出限制、CLI/HTTP/快照/UI交接；前端构建及 Windows 已扩展旧工作区升级测试按现行规则执行。此为候选范围，未声称完成任何上述验证。
